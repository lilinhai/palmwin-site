# 中文输入为什么是远程桌面的老大难

> RDP 协议里，键盘输入有两种表达方式：**扫描码**和 **Unicode 字符**。看起来随便挑一个能用的就行，实际上这两条路通向完全不同的结果，而且软键盘和物理键盘要用相反的那一条。

## 一、扫描码：告诉远端「你按了哪个键」

扫描码描述的是物理键位。你按下 A 键，客户端发的是「A 这个位置被按下了」，至于这一刻 A 应该产生什么字符，由远端的键盘布局和输入法决定。

它的好处是行为完全和本机一致：Shift 组合、Caps Lock、输入法组词、快捷键，全都正常。它的坏处是——只有当屏幕上的字符由远端产生时，这条路才成立。

## 二、Unicode：直接告诉远端「我要这个字」

Unicode 通道发的是一个码点。Windows 收到后做的是「把 U+4E2D 这个字符投递给前台程序」，走的是系统级的字符注入，**绕过输入法**。

这就是关键矛盾：手机软键盘打中文时，字已经在手机上组好了（你看到候选词、选了「中」），到客户端手上就是一个确定的中文字符。这时用 Unicode 是对的——远端不需要再组一遍词。

但如果手机接的是物理键盘，用户在 PC 模式下敲拼音、指望 Windows 的微软拼音弹出候选框，那必须发扫描码。用 Unicode 的后果是：每个字母单独投递给前台程序，输入法完全收不到按键，所以永远不组词。你在远端打出一串英文字母，这就是「中文输入失效」的真相。

> 一句话判据：**字符已经在手机侧组好 → 发 Unicode；要让远端去组 → 发扫描码。**

## 三、软键盘这一侧还有第二个坑

手机软键盘弹出后，安卓的输入法框架会接管输入法连接（InputConnection）。如果客户端只是把文本框的输入连接拒绝了，输入法可能仍在屏幕上但你不收任何字符；如果只是「把键盘收起来」，输入法连接仍然存在，某些设备上物理键还是会被交给输入法窗口，而不是给应用。

所以「关掉软键盘」不是一次调用能完成的，至少要四步：让这个视图不再声称自己是文本编辑器、重启一次输入法会话、用窗口令牌收走视图、把焦点还给真正接收按键的视图。

## 四、物理键盘这一侧：有些键根本到不了你的代码

这一点在安卓上非常反直觉。Win 键、Alt+Tab、Ctrl+Esc、Alt+F4 这些组合，在系统层就被消费掉了——Win 会切桌面或多任务，Alt+Tab 会切安卓应用，Alt+F4 会关掉前台应用。你的按键回调里根本收不到这些事件，日志里一条都没有。

这不是代码没写对，是系统优先级更高。唯一的补救是给这些操作做**应用内的按钮入口**：面板上放一排「Win」「Alt+Tab」「Ctrl+Esc」「Alt+F4」「任务管理器」之类的按钮，点击时由应用按「修饰键按下 → 主键按下 → 主键抬起 → 修饰键抬起」的顺序发扫描码。

顺序不能错。Windows 判断一个组合键，依据是「主键按下的那一刻，修饰键是否处于按下状态」。抬起也必须逐个补发，漏一个释放事件，远端会认为 Ctrl 一直按着，之后所有输入都变成组合键。

## 五、Ctrl+Alt+Del 是另一回事

Windows 从键盘来源拦截 Ctrl+Alt+Del，这是安全设计（保证登录界面不能被伪造）。所以按普通组合键发三个扫描码，本地能成功，远端可能不响应。协议里有一个专门的能力位，告诉服务端「这个客户端会自己处理安全注意序列」，打开之后普通扫描码序列才被接受。

顺带一提，协议里还有一个「同步键状态」的消息，很多人以为它是发 Ctrl+Alt+Del 的。它不是——它只是重新声明 Num Lock / Caps Lock 这些锁键的当前状态。

## 六、还有个更隐蔽的：输入法归属

在华为的电脑模式下，如果软键盘是弹开状态，系统会把物理键盘的按键交给输入法窗口，而不是交给应用。这时应用侧任何「响应按键再补救」的代码都是死代码——它在等的事件，正好被它想修的那个状态挡在门外。

正确做法不是补，而是**让那个状态一开始就不产生**：真正关掉输入法连接，而不是只把键盘视图收起来。

我在这个问题上写过一版「看起来很有道理」的补救逻辑——在按键入口检查是不是物理键、是的话先把软键盘收掉。那一版上线后用户的反馈是「还是不行」。删掉它，改成从根源上不让输入法连接存在，问题才消失。
