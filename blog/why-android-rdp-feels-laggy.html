为什么安卓上的远程桌面会「卡」

很多人第一次用手机连 Windows，把「卡」归因于网速。我在局域网里测过：同一台机器，用官方客户端也卡，网速根本不是瓶颈。真正的原因在渲染路径上。

一、画面是怎么走到屏幕上的

RDP 服务端把屏幕切成更新内容，一条一条发过来。客户端解出来之后，需要把它变成屏幕上的像素。这一步看起来简单，但有三个完全不同的层次：

  1. 解码。可能是纯位图，可能是 RLE 压缩，可能是远程 FX 编解码，也可能是 H.264。
  2. 合成。把解出来的小块贴进客户端自己维护的一整张屏幕缓冲区。
  3. 上屏。把那张缓冲区交给屏幕。

大部分「卡」发生在第 3 步，不在第 1 步。

二、慢的那条路：解到内存，再拷给界面

如果客户端把解出来的每一帧先拷进一块 Java 层的位图，再通过普通控件画到屏幕上，那么每一帧都要发生一次整屏拷贝，还要经过一次跨语言调用和一次图形 API 上传。滚动网页这种「整个屏幕都在动」的操作，等于每帧都在搬几百兆像素/秒的数据。

用一句话判断：如果滚动的时候整屏都在重画，而不是只有内容区在变，那这条路基本就没走对。

三、快的路：解到哪里，就从哪里上屏

把「解码后的像素」和「屏幕上的像素」合成同一块内存，就没有拷贝了。具体做法是：客户端自己申请系统可绘制的图形缓冲区，把它锁住，拿到这块内存的地址和步长，然后让协议栈把解码结果直接写进去。协议栈的图形层本来就支持「外部提供的缓冲区」，只要在初始化时传进去即可。

这里有三个容易踩的点：

  • 缓冲区释放权必须留在自己手里。如果让协议栈去释放那块系统图形内存，会出问题。
  • 更新到达的回调里不能做耗时操作——它持有更新锁，返回后才释放。这个回调里只该做两件事：算脏矩形，提交缓冲区。
  • 设备旋转或分辨率变化时必须先解锁旧缓冲区再重建，否则会锁死。

四、脏矩形：只提交变了的区域

协议栈每次收到更新，会记录被改动过的矩形。客户端在提交前把所有矩形合成一个包围盒，只把这一块交给屏幕。对「移动窗口」「打字」「拖滚动条」这类局部变化，代价从整屏变成一小块。

注意包围盒策略有代价：如果屏幕上同时有两个相距很远的角落变化，包围盒会把中间一大片没变的区域也提交。这是简单的取舍——真实使用中局部变化远多于对角变化，值得。

五、还有一个更大的坑：图形管线根本没协商

上面说的都是「拿到帧之后怎么显示」。但如果图形管线（RDP 里叫 GFX 通道）根本没建立，服务端就只能发最原始的位图更新，滚动时整屏都在变，前面所有优化都白做。

这个通道需要客户端在连接参数里显式打开，默认是关的。打开之后，服务端会重新按帧、按变化的区域来编码，滚动才可能变成局部刷新。

更隐蔽的一点：即使服务端建立了这个通道，如果客户端收到「通道已连接」的通知后没有转调协议栈自己的处理器，那么解码回调根本没注册，帧到了也不认。表现就是「明明协商成功了，画面还是不流畅」。

六、锯齿是怎么回事

锯齿通常和性能无关，和非整数倍缩放有关。远端桌面是 1920×1080，手机屏幕是 1170×2532，如果客户端把画面拉伸到刚好铺满，每个远端像素对应 1.37 个屏幕像素，采样点落在像素中间，边缘就会软、文字就会毛。

两个方向可以解决：

  • 让上屏这一层负责缩放，用系统的合成器去插值（它至少做的是双线性）。
  • 更好的办法：直接把「远端分辨率」改成和显示区域成整数比。RDP 支持客户端主动请求改变远端桌面尺寸，这条通道叫显示控制（Display Control）。连上之后请求把远端改成 1280×720 或 2560×1440，1:1 渲染，文字就实了。

七、顺序很重要

最后一条不是技术，是排查顺序。遇到「卡」，按这个顺序问：

  1. 图形管线协商成功了吗？（看日志里通道列表）
  2. 更新回调注册上了吗？（通道连上后有没有转调通用处理器）
  3. 上屏是零拷贝还是每帧整屏拷贝？
  4. 提交的是脏矩形还是整屏？
  5. 缩放是整数倍吗？

前两条不满足，后面三条调得再细也没用。我在这个项目上前两次「优化」都白做了，因为第一层就没通。
