怎么判断「光标在不在输入框里」

这是一个看起来很蠢的问题：远程桌面的画面是一张位图，客户端根本不知道远端哪个控件是输入框。而它必须知道——只有知道，才能决定什么时候该弹软键盘。

这个判断我连错了三次，每次都换了一种「更聪明」的信号，每次都被真机打穿。这篇文章记的是这个过程，以及最后落地的判据。

一、为什么客户端必须知道

软键盘弹出来会遮掉半屏，而且会改变手机的输入法归属。所以不能一直弹着，也不能用户点哪儿都弹。理想行为是：

  • 光标进入一个可编辑的文本框 → 弹键盘
  • 光标离开 → 收键盘
  • 光标在不可编辑的文字上 → 不弹

客户端手里只有图像，所以所有的判断都只能是从图像或协议里推断。

二、第一次尝试：看远端光标形状

Windows 会给不同的控件换不同的鼠标指针。文本输入区是竖细的「I 形」（insertion point），普通区域是箭头。RDP 协议会把指针形状作为单独的消息发过来，客户端能拿到位图。

于是第一版：如果指针形状是竖细 I 形，就认为在输入框里。

这一版在真机上「基本能用」，但问题很多。最典型的是：浏览器正文、Word 的只读视图、Windows 设置里的说明文字，都给出 I 形光标——因为 I 形在 Windows 里的语义其实是「文字可以被选中」，不是「文字可以被编辑」。

这是这一整条路的根本局限：光标本位描述的是「这里能做什么操作」，不是「这里能不能输入」。客户端拿不到后者。

三、第二次尝试：看脏矩形里有没有「细条」

既然光标形状不可靠，就换一个信号：真正的文本插入符会闪烁。闪烁意味着那一小块区域每隔半秒左右会重绘一次，形状是一条很细的竖条（宽 1~2 像素、高十几到几十像素）。

于是第二版：连上之后监视一小段时间内的更新，如果脏矩形里出现「细条」形状，就是可编辑的输入框。

结果更糟：命中次数恒为 0。

我去读协议栈的实现才发现，脏矩形是按 64×64 的大块标记的，一条 64 像素宽的大矩形里包含 2 像素宽的插入符，客户端没办法从中分离出「这里有一个细条」。

观测点选错了层。 我在看「过程」（脏矩形怎么标记），而真正的「结果」是「像素到底变没变」。过程会被压缩、合并、裁剪，结果不会。

四、第三次尝试：直接比较像素

改成不看脏矩形，直接在被观察区域取一小块像素（12×80），每隔一小段时间和上一次的副本比一次。变了就记一票。

这一次终于命中了。但判决逻辑又错了：我把「一个采样窗口内没有变化」当成了「这里是静态文字，不是输入框」，于是收键盘。

真机上的后果是：用户一开始打字，键盘就消失。

原因是 Windows 在用户输入时会把插入符从闪烁改成常亮。常亮意味着那块像素完全不变，于是被判成「静态只读文字」。

这个观测同时对应两个完全相反的结论（只读文字 / 正在输入），所以它不是判据。它能做的只有正向确认：变了 → 肯定在输入；没变 → 什么都不能说。

五、最后落地的判据

现在用的是两条互补的规则：

  1. 形状给方向：指针形状是竖细 I 形 → 认为「可能在文本框里」，允许弹键盘。形状变成非 I 形 → 认为「离开了」，收键盘。这一条是边沿触发（形状变化时才动作），不会反复抖。
  2. 像素给确认：在怀疑是输入框时，采样一小块区域的像素变化。有变化 → 确认在输入，保持键盘。没有变化 → 不下结论，保持键盘。

关键是第二条的最后一支：「没观察到」绝不能推断成「不具备」。这个错误我在这个项目里犯了三次，三次都是同一个思维：把「信号缺席」当成「反面证据」。

判据一句话：如果一个观测在「是」和「不是」两种情况下都会给出相同的结果，它就只能用来做正向确认。

六、还有两条必须处理的边角

指针被隐藏 ≠ 光标离开。 Windows 在用户打字时会主动隐藏鼠标指针，协议里发的是「这一帧不带位图」的指针更新。如果把它理解成「光标离开了文本框」，就会在用户打字的瞬间收掉键盘。这条我单独踩了一次，症状是「打个标点符号键盘就没了」。

边沿触发的状态机对假边沿没有自愈能力。 形状判断是边沿触发的，一旦某一帧错误地被判成「非文本」，状态就翻过去了，而且后面每一帧都因为「状态没变」而被忽略。所以必须在别处补一个「电平复查」：过一段时间重新看一次当前状态，而不是只依赖变化事件。

七、一句话总结

不要试图从画面里「算出」远端某个控件是不是输入框——信息不够。要做的是：用弱信号给出方向，用强信号给出确认，任何不确定的情况下都停在「保持现状」而不是「收回」。用户的键盘被莫名收起，比它在不该出现时出现更让人恼火。
